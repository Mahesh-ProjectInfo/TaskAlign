Why This Design? (Architectural Reasoning)
Why don't we store OTP?
OTP is temporary data. It is generated during password reset, stored in an in-memory HashMap, sent using SMTP, and discarded after verification or expiration. Persisting it in the database would add unnecessary complexity without business value.

Why store the profile picture path instead of the image?
Images are stored in the file system, while the database stores only the file path. This keeps the database lightweight and improves performance.

Why use TIMESTAMP?
created_at and updated_at are audit fields. Using TIMESTAMP with Spring Data JPA (LocalDateTime) provides automatic timestamp management and aligns well with MySQL and Hibernate.

Why use soft delete?
Soft delete preserves assignments and historical assignment data while preventing deleted users from accessing the application.
Final Verdict
The users table is fully normalized (3NF), optimized for Spring Boot, Spring Data JPA, MySQL, Spring Security, JWT Authentication, SMTP-based password reset, JasperReports, and Apache POI. It provides a clean foundation for the authentication module while remaining scalable and easy to maintain.

Why This Design? (Architectural Reasoning)
Why create a separate Assignment Types table?
Assignment Types are reusable master data. Storing them once avoids duplication across Roles, Skills, Resources, and Assignments, ensuring consistency throughout the application.

Why don't we store Assignment Names here?
An Assignment Type defines the category (e.g., Software Project Assignment), whereas an Assignment Name (e.g., Employee Payroll System) is created each time a new assignment is added.
Therefore:
Assignment Types belong in this master table. 
Assignment Names belong in the assignments table. 
This establishes a One-to-Many relationship:
Software Project Assignment

        â”œâ”€â”€ Employee Payroll System
        â”œâ”€â”€ Hospital Management System
        â”œâ”€â”€ Banking Portal
        â””â”€â”€ Inventory Management System

Why include created_by and updated_by?
These fields provide complete auditability by recording who created and last modified the Assignment Type. This is a common enterprise requirement that helps maintain accountability and traceability of master data changes.
Why use Soft Delete?
Soft delete prevents accidental removal of Assignment Types that are already referenced by Assignments, Roles, Skills, or Resources, preserving historical data and referential integrity.

Overall Design Justification
The assignment_types table acts as the foundation of the Master Data module. It centralizes reusable assignment categories, maintains referential integrity, supports auditing through created_by and updated_by, and is fully compatible with Spring Boot, Spring Data JPA, MySQL, JasperReports, and Apache POI. It follows Third Normal Form (3NF) and is designed to scale as new assignment categories are introduced in the future.

Why This Design? (Architectural Reasoning)
Why create a separate Roles table?
Roles are reusable master data. Multiple Resources can share the same Role, so storing Roles in a separate table eliminates duplication and ensures consistency across the system.

Why relate Roles to Assignment Types?
Roles are specific to a business domain.
For example:
Backend Developer belongs to Software Project Assignment. 
Civil Engineer belongs to Construction Project Assignment. 
This relationship ensures that only relevant Roles are available when creating Resources or Assignments for a selected Assignment Type.

Why doesn't this table include a Description field?
The current application UI only requires Assignment Type and Role Name for creating and managing Roles. Role names are self-explanatory (e.g., Backend Developer, QA Engineer, Machine Operator), making a separate Description field unnecessary. Removing it simplifies both the database and the user interface.

Why include created_by and updated_by?
These fields provide complete auditability by recording who created and last modified each Role.

Why use Soft Delete?
Soft delete preserves historical relationships with Resources and Assignments while preventing deleted Roles from being assigned to new Resources.

Overall Design Justification
The roles table centralizes reusable job roles, categorizes them by Assignment Type, supports auditing, and enables efficient reuse across Resources. The design follows Third Normal Form (3NF) and is fully compatible with Spring Boot, Spring Data JPA, MySQL, JasperReports, and Apache POI. It provides a scalable, maintainable, and enterprise-ready foundation for the Role Master module.

12. Why This Design? (Architectural Reasoning)
Why create a separate Skills table?
Skills are reusable master data. A single Skill such as Java or Negotiation can be assigned to multiple Resources and required by multiple Tasks. Storing Skills separately eliminates duplication and ensures consistency.
Why relate Skills to Assignment Types?
Skills are domain-specific. For example:
Java belongs to Software Project Assignment. 
Brick Work belongs to Construction Project Assignment. 
This ensures users can only select relevant Skills based on the chosen Assignment Type.
Why doesn't this table include a Description field?
The Skill Master UI only requires Assignment Type and Skill Name. Skill names are concise and self-explanatory, so an additional Description field would add unnecessary complexity.
Why include created_by and updated_by?
These fields provide complete auditability by recording who created and last modified each Skill.
Why use Soft Delete?
Soft delete preserves historical relationships with Resources and Tasks while preventing deleted Skills from being used in new records.
Overall Design Justification
The skills table centralizes reusable competencies, categorizes them by Assignment Type, and serves as the foundation for the Business Rule Engine and the Hungarian Algorithm. The design follows Third Normal Form (3NF) and is optimized for Spring Boot, Spring Data JPA, MySQL, JasperReports, and Apache POI. It provides a scalable and maintainable foundation for skill-based resource assignment.

12. Why This Design? (Architectural Reasoning)
Why create a separate Resources table?
Resources are reusable across multiple assignments. Storing them once avoids duplication and allows Assignment Managers to select existing Resources rather than recreating them.

Why are Skills stored separately?
A Resource can have multiple Skills, and a Skill can belong to multiple Resources. This is a Many-to-Many relationship and is normalized using the resource_skills table.

Why store Monthly Salary instead of Cost Per Day?
Cost Per Day is calculated using the Resource's Monthly Salary and the Assignment's Working Days Per Month. Since it is a derived value, storing it would introduce redundancy and potential inconsistency.

Why allow duplicate Resource Names?
Names are not guaranteed to be unique in real organizations. The resource_id uniquely identifies each Resource.

Why use Soft Delete?
Resources may already be referenced by historical Assignments and Reports. Soft delete preserves those relationships while preventing deleted Resources from being used in future assignments.

Overall Design Justification
The resources table is the central entity of the Resource Management module. It provides reusable Resource information, supports cost and performance optimization, integrates seamlessly with the Business Rule Engine and Hungarian Algorithm, and is fully compatible with Spring Boot, Spring Data JPA, MySQL, JasperReports, and Apache POI. It follows Third Normal Form (3NF) and provides a scalable foundation for the Task Align optimization engine.

12. Why This Design? (Architectural Reasoning)
Why create a separate resource_skills table?
A Resource can possess multiple Skills, and the same Skill can belong to multiple Resources. This is a Many-to-Many relationship, which is resolved using a junction table to maintain normalization.

Why not store Skills directly in the resources table?
Storing multiple Skills in a single column (e.g., "Java, Spring Boot, REST API") violates the First Normal Form (1NF), makes searching difficult, and prevents efficient joins and comparisons. Separating Skills into a mapping table keeps the database normalized and scalable.

Why use a surrogate primary key instead of a composite key?
Using resource_skill_id simplifies Spring Data JPA entity mapping, repository operations, and future enhancements. A composite primary key would require @EmbeddedId or @IdClass, increasing implementation complexity.

Why add a UNIQUE constraint on (resource_id, skill_id)?
This prevents assigning the same Skill to the same Resource more than once while still allowing a Resource to have multiple different Skills.

Why aren't Skills filtered by Role?
Roles represent a Resource's designation, while Skills represent the Resource's actual competencies. Resources with the same Role can possess different Skills. Therefore, Skills are loaded based on the selected Assignment Type, and the Assignment Manager selects the actual Skills possessed by the Resource.

Overall Design Justification
The resource_skills table is a lightweight junction table that resolves the Many-to-Many relationship between Resources and Skills. It supports the Business Rule Engine, enables accurate skill matching during assignment generation, and maintains a normalized database structure. The design is fully compatible with Spring Boot, Spring Data JPA, MySQL, JasperReports, and Apache POI, while remaining flexible for future enhancements such as skill proficiency levels or years of experience.

The assignments table serves as the central transactional entity of the Task Align system. 12. Why This Design? (Architectural Reasoning)
Why create a separate assignment_resources table?
An Assignment can include multiple Resources, and a Resource can participate in multiple Assignments. This is a Many-to-Many relationship that is resolved using a junction table to maintain normalization.

Why not store selected Resources directly in the assignments table?
Storing multiple Resource IDs in a single column would violate the First Normal Form (1NF) and make searching, filtering, and joining difficult. A separate mapping table keeps the design normalized and scalable.

Why use a surrogate primary key instead of a composite key?
Using assignment_resource_id simplifies Spring Data JPA entity mapping, repository operations, and future enhancements. Composite primary keys would require @EmbeddedId or @IdClass, increasing implementation complexity.

Why add a UNIQUE constraint on (assignment_id, resource_id)?
This prevents the same Resource from being selected multiple times for the same Assignment while still allowing the Resource to participate in different Assignments.

Why doesn't this table store Salary, Role, or Performance Rating?
Salary, Role, and Performance Rating are already maintained in the resources table. Storing them again would introduce redundancy and violate database normalization. Whenever these values are required, the application retrieves them through the resource_id relationship.

Why does removing a Resource from an Assignment not delete it from Resource Management?
The resources table is the master repository of all Resources. Removing a Resource from an Assignment only removes the association in the assignment_resources table, allowing the same Resource to be reused in future Assignments.

Overall Design Justification
The assignment_resources table provides a normalized and reusable mechanism for associating Resources with Assignments. It supports resource selection during Assignment Creation, serves as the input to the Business Rule Engine and Hungarian Algorithm, and enables efficient resource reuse across multiple Assignments. The design follows Third Normal Form (3NF) and is fully compatible with Spring Boot, Spring Data JPA, MySQL, JasperReports, and Apache POI.
